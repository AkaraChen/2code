## 你不是在并行，你是在轮询

设想一个很普通的下午。你开了三个 agent：一个在重构 API，一个在修一个 flaky 测试，一个在试一个你还没想清楚的方案。

然后你做了什么？

你每隔两三分钟切一圈窗口。第一个还在跑。第二个不知道停在哪一步，看起来像是在等你确认，但也可能是卡住了。第三个的输出已经滚过去一屏，你得往上翻才知道它到底改了什么。切完一圈，回到你自己那件事上，三十秒后又忍不住切一圈。

这不叫并行。这叫**人肉轮询**。

而轮询的成本有个很难受的性质：**它随 agent 数量增长，但你的注意力不会**。加到第四个、第五个 agent，模型没有变慢，token 也没有变贵。变贵的是"我现在到底有几件事在跑、跑到哪了"这个问题的答案。

一句话钉死：**并行的真正摩擦不是 token，是你看不见 agent 在干什么、干到哪了。**

## 三种"瓶颈叙事"

有意思的是，这一轮做工具的人都同意「瓶颈已经不在模型」，但对瓶颈到底是什么，答案完全不同。

| 产品 | 他们说的瓶颈 | 原话 |
| --- | --- | --- |
| Superset | agent 的**数量**与编排 | *"The real bottleneck isn't agent quality. It's agent quantity."* |
| Superset（100 agents 路线图） | **人类 review** 扩不过去 | *"Scale the agents all you want - it's the humans that don't scale."* |
| JetBrains Air | **工作流**：不切应用、留在掌控里 | *"I was able to fix small things quickly without switching applications."* |
| **2code** | **可见性** | agent 是否在跑、跑完没有、结果在哪、多条线是否一眼扫得清 |

这三种判断都不错，而且彼此不冲突。但它们都跳过了一个更靠前的问题。

编排的前提是你知道有什么在跑。review 的前提是你知道结果在哪。"留在掌控里"的前提是——你**看得见**。

**在你需要一层编排之前，你先需要一层可见。**

大多数人卡住的位置，不是"我调度不了 50 个 agent"，而是"我同时跑三个，就已经不知道谁跑完了"。

## 什么叫"可见性"

**可见性（visibility）= Agent 以及它背后那摊活，对你是否一眼可见、可跟进、可交接。**

具体是这几件事：

**谁在跑、谁跑完了、谁卡住了。** 不用切十个窗口人肉确认。完成这件事应该主动找上你，而不是等你去查。

**半截的东西还在不在。** 那个跑到一半的 agent 会话、那个你启动了就忘了的 dev server——它们还活着吗？输出在哪？还是说你已经在同一个端口上起过两次了。

**结果在哪。** Agent 说它改完了。改了哪些文件、diff 长什么样、能不能扫一眼就判断要不要合——这中间隔着几次应用切换？

**切走再回来，工作有没有"还看得见"。** 切 worktree、关掉笔记本、第二天早上打开。这三条任务线是回到原样，还是变成三个你要重新考古的黑盒？

注意这里的反面不是"没有数据"，而是**数据都在，只是散落在十个你必须亲自去看的地方**。终端里其实什么都有：输出在、进程在、git 状态在。问题是没有任何一层东西把它们汇总成"你一眼能扫完"的形式。

**可见性不是仪表盘崇拜。** 恰恰相反：可见性做得好的标志是**你大部分时候不需要看**——因为该找你的时候它会找你。

## 并行怎么把"看不见"放大

单个 agent 时，看不见的成本很小：你多等了两分钟才发现它早就跑完了。烦，但可以忍。

并行之后，这个成本不是乘以 N，而是比 N 涨得快，因为三件事同时发生：

**一，每次扫描要看 N 个地方。** 三个 agent，一圈就是三次窗口切换、三次"我刚才在这儿看到哪了"的重新定位。

**二，扫描频率也上升。** 跑的东西越多，"是不是有谁好了"这个念头出现得越频繁。于是你切得更勤，而每次切换都要付一次上下文重建。

**三，最贵的一条：并行会让你不敢离开。** 因为一旦离开，回来时你不知道状态，所以你干脆守着。**这就把并行的收益吃掉了**——你并行的本意是"让 agent 干活的时候我去干别的"，结果你把自己变成了调度器。

再加上一个硬断点：**重启或切换会让可见性直接归零。** 代码没丢，git 里都在。丢的是"哪条线在干嘛、跑到哪了、下一步是什么"。一次重启，三条线一起变黑盒——而这在并行下是常态，不是意外。

所以"多开几个终端窗口"从来不是并行工作流。它只是把同一个盲区复制了 N 份。

## 2code 怎么做：把可见性当一等公民

2code 是一个完整的终端模拟器——你的 shell、prompt、别名、CLI agent 全部照常工作。区别在于，它把上面那四个问题当成产品的一等公民，而不是留给你的肌肉记忆。

**Agent 状态感知：把轮询换成推送。** 2code 从终端输出、标题序列和进度序列里识别 agent 状态。跑完了，绿点亮起，声音响一下。你不再需要"每两分钟切一圈"——**这一条直接删掉了轮询这个动作本身**。

**持久终端 + 恢复：切走再回来还看得见。** 终端会话、scrollback、窗口布局在重启后恢复。你回来看到的是离开时的样子，而不是三个空白窗口和一次考古。

**Worktree 窗口：位置即身份。** 每个 worktree 一个独立窗口，各自带着自己的终端和上下文。三条泳道在空间上就是分开的——你不需要靠标签页命名记住"哪个窗口在修 bug"。Worktree profile 建在 `~/.2code/workspace/{id}`，创建时跑你在 `2code.json` 里定义的 setup script，删除时跑 teardown。

**内置 git 与轻量编辑器：结果在哪，一眼可见。** Diff、暂存区、提交历史就在同一个 App 里。Agent 说改完了，你扫一眼 diff 就能判断要不要合，中间没有 Cmd-Tab。

这四条串起来是同一句话：**普通终端只负责把字符画到屏幕上。至于那些字符背后有几件事在跑、跑到哪了，它不管。2code 管。**

## 边界：这不替代编排器，也不替代 ADE

说清楚比说满更重要。

如果你真的要同时调度几十个 agent、需要自动化 review 关卡和任务分配，那是 Superset 那一层在解的问题，2code 不做这个。如果你想要的是一个围绕 agent 重建的 IDE、把编辑与 review 收进同一个界面，那是 Air 的方向。

2code 解的是更靠前、也更日常的一层：**你每天工作台上的那两三条任务线，是不是一眼看得见。**

这一层没做好，上面那两层都会打折——编排器能帮你起 50 个 agent，但你桌面上那三个到底跑完没有，仍然要有人告诉你。

## 试一下

如果你认得下面这个场景——

你起了三条线，然后**离开去做别的事**。二十分钟后绿点亮起、声音响了，你回来扫一眼 diff，合掉一条，让另外两条继续。晚上关掉 App，第二天打开，三条线还在原地，你知道每条跑到哪了。

——那说明你缺的不是更快的模型，是可见性。
