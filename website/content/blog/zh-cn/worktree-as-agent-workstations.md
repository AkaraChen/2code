## 早上九点：一个仓库，三张桌子

我打开 2code，不是先写代码，是先开工位。

今天同时要推进三件事：

1. **修 bug**——线上有个偶发 500，日志已经钉到某条查询
2. **写功能**——用户设置页要加一个导出按钮，PR 今天最好能出草稿
3. **做实验**——想换一种缓存策略，还不知道能不能成，别污染主线

过去我会在同一个 checkout 上切分支，或者开三个 Terminal 窗口各自 `cd` 到不同目录，然后指望自己记得「左边那个是修 bug 的」。

现在的标准动作是：**一个任务 = 一个 agent 工位 = 一个 Git worktree**。

在 2code 里，工位就是 profile：创建时自动 `git worktree add`，落在 `~/.2code/workspace/{id}`，各自一条分支、一套终端，需要的话再挂一个自己的 dev server。创建脚本写在项目根的 `2code.json` 里——比如 `npm install`——新工位起来时自动跑，不用我每条线手敲一遍依赖安装。

九点十五，三条任务线都亮着：修 bug / 写功能 / 实验。每条工位里起一个 CLI agent（Claude Code，或你顺手的那个），需要热重载的那两条再挂上 dev server。然后我把注意力留给自己：读 issue、回消息、写那份其实今天最该先写完的设计备注。

Agent 在工位上干活。我不盯着它们。

## 为什么「一份工作副本」不够用了

Git 的经典模型假设你一次只改一件事：checkout 一条分支，改完，提交，再切下一条。

Agent 把这个假设打碎了。

一个 agent 会跑十几分钟，甚至更久。它改文件、跑测试、自己兜圈子。你如果还在同一份工作副本里开第二个 agent，结果往往是：

- 两个 agent 改到同一批文件，diff 变成一锅粥
- 你想切分支去救火，第一个 agent 的半成品工作区跟着乱
- dev server 端口被占，你分不清是谁起的、该杀哪个
- 合代码时你分不清「这行是谁改的、为了哪件事」

Worktree 不是高级 Git 炫技。它只是把一件早就该成立的事说了出来：**并行任务需要并行工作副本**。

官方文档在 [git-worktree](https://git-scm.com/docs/git-worktree)。简单说：同一个仓库可以有多份检出，共享对象库，目录和分支各自独立。对 agent 来说，就是每条任务线有自己的文件树，互不踩脚。

我把它记成：

> **工位 = 独立 worktree + 终端 + agent（+ 可选 dev server）**

英文里你可以说 swimlane。中文里，**工位**更贴——每张桌子上坐着一个 agent，你走过来验收，而不是所有人挤在同一张桌子上抢键盘。

## 中午：绿点亮了，先看 diff

十一点半，侧边栏有个工位亮了绿点。声音响了一下。

不用切四个 Terminal.app 窗口人肉轮询。2code 从终端输出、标题和进度序列里识别 agent 状态——跑完了它会来找你，而不是等你去查。

我点进「修 bug」那条工位，打开内置 git diff。

Agent 说它修好了。Diff 说：它改了查询、加了测试，还顺手「整理」了一个不相关的工具函数。最后那下我回滚掉，前两处留下。自己补了两行注释，跑一遍相关测试，合进主线。

另外两条还在跑。我没有去戳它们。

这是并行真正省下来的东西：**你离开去做别的事，做完了它会来找你；回来时结果就在工位旁边，不用跨三个 App 考古。**

## 下午：合一条，挂一条，重启也不怕

两点，「写功能」那条也亮了。Diff 干净，我 review 完开了 draft PR。

「实验」那条还在吐日志，缓存策略看起来方向不对。我没有急着杀它——下午还有会，先挂着。工位还在，终端 scrollback 还在，agent 会话还在。会议结束再回来，不会塌成三个空白窗口加一次 `git status` 考古。

四点半，笔记本合盖去楼下。回来打开 2code：

- 三个工位还在侧边栏
- 每条工位的终端历史还在
- 未合完的改动还在各自 worktree 里
- 我记得（系统也记得）哪条是实验、哪条已经开了 PR

持久终端和会话恢复，在这里不是「好用的小功能」，是并行工作流的底线。**切走再回来，工位还是工位，不是三个你要重新认领的黑盒。**

## 在 2code 里，一天对应哪些动作

把上面的故事拆成可复现的操作，大概是这样：

| 时刻 | 你做什么 | 对应能力 |
| --- | --- | --- |
| 早上 | 按任务建 2–3 个 profile | Worktree 工位（独立分支 + 目录） |
| 早上 | 每条工位起 agent / dev server | 持久终端 + 命令模板 |
| 白天 | 去做别的事 | Agent 完成绿点 / 声音提醒 |
| 完成时 | 扫 diff、改一小刀、决定合或丢 | 内置 git diff |
| 打断后 | 合盖、切项目、第二天再开 | 会话与布局恢复 |
| 收尾 | 删掉实验工位 | teardown script + worktree 清理 |

不需要同时开 50 个 agent。**两三条真实任务线，跑一整天**，已经够用，也已经够暴露普通终端的问题。

## 什么时候该停 agent，什么时候该自己改

并行不是把判断外包出去。我自己的启发式很土，但好用：

**让 agent 继续跑，如果：** 任务边界清楚（复现步骤、验收标准都在）、失败了重跑成本低、你暂时抽不出整块注意力。

**自己上手，如果：** diff 里开始出现「顺手重构」、测试在同一处失败第三次、你已经能用三句话写出正确补丁。Agent 最贵的时刻往往不是 token，是你看着它第三次走错路口，还在礼貌等待。

**直接关工位，如果：** 实验已经证伪，或者方向变了。半成品 worktree 留着会占注意力。删掉 profile，teardown 跑完，目录和分支清掉，脑子也清掉。

工位的价值不只是「能并行」，还有**能干净地结束**。

## 踩过的坑（你大概也会踩）

**依赖装两遍、三遍。** 每个 worktree 是独立工作目录，`node_modules` 不会自动出现。把 `npm install` / `bun install` 写进 `2code.json` 的 setup，比每次想起来再装要稳。

**端口冲突。** 三条线都起 `localhost:3000`，后起的会挂。给实验线换端口，或者约定「同时只热一条 UI」。工位隔离的是文件树，不是你的端口表。

**合并顺序。** 先合小的、冲突面小的；实验线永远最后，或者从来不合。三条线都从同一点切出来时还好；拖了一天之后，记得先 rebase/merge 主线再继续，别让 agent 在过期的基线上勤奋劳动。

**不要为了并行而并行。** 一条线能做完的事，硬拆成三个 agent，review 成本往往高于收益。工位是为「本来就会并行的任务」准备的，不是绩效指标。

## 试一天

如果你愿意用一天验证这个模型，最小路径是：

1. 装 2code（macOS）：

```bash
brew install --cask akarachen/tap/2code
```

2. 加一个你正在做的真实项目
3. 开**两个**工位就够：一个修眼前的 bug，一个做你本来就会分心去做的小事
4. 每条工位起一个 agent，然后强制自己离开二十分钟
5. 绿点亮了再回来，只看 diff，决定合、改、或丢

——如果你在第 4 步忍不住去轮询窗口，说明旧习惯还在；如果第 5 步你能在一个 App 里看完结果，说明工位模型开始工作了。
